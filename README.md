# keel

Сборка и восстановление хоста Proxmox VE по описанию.

Репозиторий — это **план восстановления, который умеет исполнять сам себя**.
В нём лежит один файл с описанием хоста, набор небольших провайдеров, которые
приводят хост к этому описанию, и документация на то, что руками (BIOS, диски,
ключи). Переустановил Proxmox с нуля — поставил keel одной командой, нажал
«применить», пошёл пить чай.

Название — от киля: то, с чего начинают строить корабль и что держит всю
конструкцию.

> **Статус: все области перенесены на Go.** Логика покрыта тестами (включая
> дословную проверку команд, которые keel отдаёт Proxmox), но на живом хосте
> ещё не обкатана — см. [что проверено и что нет](docs/PLAN.md#проверено-и-не-проверено).

Для работы нужен интернет: без него не скачать ни образы гостей, ни пакеты, а
значит и восстанавливать нечего. Офлайнового режима у keel нет намеренно.

## Установка

```bash
bash -c "$(curl -fsSL https://keel.example.com/install.sh)"
```

Ставится один статический бинарник. Зависимостей нет никаких: ни `perl`, ни
`whiptail`, ни даже совместимой libc. Инструмент восстановления, который перед
работой просит что-то доустановить, — плохой инструмент восстановления.

Скачанное сверяется с контрольной суммой, и от тебя для этого ничего не
требуется. Обновиться потом — `keel update`.

Всё, с чем работаешь ты, лежит в одном каталоге `/root/keel`: манифест
`host.json`, пароли в `secrets/`, копии правленых файлов в `backups/`, планы
в `plans/`, логи в `logs/`.

## Как пользоваться

```bash
keel           # экран: состояние хоста, выбор и ход применения сразу
keel doctor    # что за хост, что с видеокартой — только чтение
keel plan      # собрать план изменений и сохранить его файлом
keel apply     # применить сохранённый план
```

Порядок `doctor → plan → apply` не формальность: `plan` показывает точный
список изменений и сохраняет его, а `apply` выполняет **именно его** — и
откажется, если хост успел измениться.

Ещё есть `keel verify` (сверить хост с манифестом), `keel backup` (снять
копию конфигурации хоста), `keel guests` (список гостей), `keel password <id>`
(пароль рабочего стола), `keel gpu revert` (откатить проброс видеокарты) и
`keel external` (каталог community-scripts — явно вне манифеста).

`й` — выход.

## Что умеет

| Провайдер | Что делает |
|---|---|
| `host/repos` | переключает apt между репозиториями Proxmox |
| `host/updates` | ставит обновления, показав список заранее |
| `host/storage` | доводит `content` хранилищ до описанного, заводит недостающие `dir` |
| `guests` | создаёт ВМ и контейнеры по манифесту |
| `host/backup` | задание vzdump по расписанию |
| `host/gpu` | отдаёт видеокарту в ВМ, с записью изменений и откатом |
| `host/config-backup` | архив конфигурации хоста плюс снимок состояния |

Гости собираются из профилей: Home Assistant OS, Debian 13, Ubuntu 24.04 и
рабочий стол — в контейнере с доступом к видеокарте хоста или в ВМ с
virtio-gl. Почему для встроенной Radeon 780M выбран контейнер, а не проброс —
[docs/30-desktop.md](docs/30-desktop.md).

## Три правила, на которых всё держится

**Правило нуля.** Нет ключа в манифесте — провайдер не делает ничего. Не
«разумный дефолт», не «обычно так лучше», а буквально ничего. Дефолтов,
меняющих состояние, в коде нет.

**Ничего вне манифеста не трогается.** Нашлась на хосте виртуалка, которой нет
в описании — keel её не удалит и не поправит. Он о ней расскажет, и всё.

**Каждое изменение проходит через одни ворота.** Провайдер не выполняет
ничего: он возвращает список шагов, а исполняет их движок — показывая команду
или diff до выполнения, снимая копию файла и записывая всё в лог. Обойти
ворота нельзя: провайдер, в котором завёлся `os/exec` или запись в файл,
роняет сборку (`internal/provider/guard_test.go`).

## Манифест

Единственный файл, который ты правишь руками — `/root/keel/host.json`. Это
JSON, но **с комментариями**: строка после `//` и блоки `/* … */`
игнорируются, висячие запятые допускаются.

```jsonc
{
  "host": {
    // Уберёшь этот ключ — keel не тронет репозитории вообще
    "repos": "no-subscription"
  },
  "guests": []
}
```

Пустой манифест `{}` означает «не трогай ничего», и keel так и поступит.
Справочник полей: [docs/MANIFEST.md](docs/MANIFEST.md).

## План — это файл

`keel plan` сохраняет набор шагов в `/root/keel/plans/`, и `keel apply`
исполняет именно его. Перед применением сверяются отпечатки манифеста и
состояния хоста: разошлись — план объявляется устаревшим.

Смысл простой: ты подтверждаешь то, что посмотрел, а не то, что программа
решит заново в момент выполнения.

```bash
keel plan --commands   # только команды, по одной на строку
keel plan --json       # то же машиночитаемо
```

## Разработка

```bash
go test ./...          # всё: разбор манифеста, провайдеры, ворота, экран
go vet ./...
docker compose up --build   # сборка и раздача, как в Dokploy
```

Посмотреть на экран глазами, не запуская keel:

```bash
KEEL_DUMP=1 go test ./internal/ui -run TestDump -v
```

Настоящие `qm`, `pct`, `pvesm`, `pvesh` в тестах не вызываются: провайдеры
возвращают шаги как данные, и тесты сверяют собранные команды дословно — это
место, где живёт большинство ошибок. Все системные пути идут через один
префикс, и при заданном `KEEL_FS_ROOT` уезжают во временный каталог, а команды
в нём записываются, а не выполняются.
