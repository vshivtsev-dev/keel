# keel

Сборка и восстановление хоста Proxmox VE по описанию.

Репозиторий — это **план восстановления, который умеет исполнять сам себя**.
В нём лежит один файл с описанием хоста, набор небольших модулей, которые
приводят хост к этому описанию, и документация на то, что руками (BIOS, диски,
ключи). Переустановил Proxmox с нуля — клонировал репозиторий, нажал
«применить», пошёл пить чай.

Название — от киля: то, с чего начинают строить корабль и что держит всю
конструкцию.

> **Статус: все фазы реализованы.** Логика покрыта тестами (включая дословную
> проверку команд, которые keel отдаёт Proxmox), но на живом хосте ещё не
> обкатана — см. [что проверено и что нет](docs/PLAN.md#проверено-и-не-проверено).
>
> **Идёт переход на Go.** Рядом с bash-версией растёт новая реализация:
> `cmd/`, `internal/`, один статический бинарник вместо `perl` и `whiptail`,
> план изменений как файл и интерфейс на Bubble Tea. Пока перенесены не все
> области — рабочей остаётся bash-версия, `bin/keel`. Что и в каком порядке
> переносится — [docs/PORT.md](docs/PORT.md).

Для работы нужен интернет: без него не скачать ни образы гостей, ни пакеты, а
значит и восстанавливать нечего. Офлайнового режима у keel нет намеренно.

## Установка

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/vshivtsev-dev/keel/main/install.sh)"
```

Скрипт кладёт код в `/root/keel/app` и делает доступной команду `keel`. Всё,
с чем работаешь ты, лежит рядом, в одном каталоге: манифест `/root/keel/host.json`,
пароли в `secrets/`, копии правленых файлов в `backups/`, логи в `logs/`.
Ничего в системе он при этом не настраивает.

## Как пользоваться

```bash
keel doctor    # что за хост, что с видеокартой — только чтение
keel plan      # что изменится — ничего не выполняется
keel apply     # применить, спрашивая перед каждым шагом
keel           # то же самое, но через меню
```

Ещё есть `keel verify` (сверить хост с манифестом), `keel backup` (снять
копию конфигурации хоста), `keel password <id>` (пароль рабочего стола) и
`keel external` (каталог community-scripts — явно вне манифеста).

## Что умеет

| Модуль | Что делает |
|---|---|
| `host/10-repos` | переключает apt между репозиториями Proxmox |
| `host/20-updates` | ставит обновления, показав список заранее |
| `host/30-storage` | доводит `content` хранилищ до описанного, заводит недостающие `dir` |
| `host/40-backup-jobs` | задание vzdump по расписанию |
| `guests/50-guests` | создаёт ВМ и контейнеры по манифесту |
| `host/60-gpu-passthrough` | отдаёт видеокарту в ВМ, с записью изменений и откатом |
| `host/90-config-backup` | архив конфигурации хоста плюс снимок состояния |

Гости собираются из профилей: Home Assistant OS, Debian 13, Ubuntu 24.04 и
рабочий стол — в контейнере с доступом к видеокарте хоста или в ВМ с
virtio-gl. Почему для встроенной Radeon 780M выбран контейнер, а не проброс —
[docs/30-desktop.md](docs/30-desktop.md).

Порядок `doctor → plan → apply` не формальность: `plan` показывает точный
список изменений, и до него ни одна команда не выполняется.

## Три правила, на которых всё держится

**Правило нуля.** Нет ключа в манифесте — модуль не делает ничего. Не
«разумный дефолт», не «обычно так лучше», а буквально ничего. Дефолтов,
меняющих состояние, в коде нет.

**Ничего вне манифеста не трогается.** Нашлась на хосте виртуалка, которой нет
в описании — keel её не удалит и не поправит. Он о ней расскажет, и всё.

**Каждое изменение проходит через одни ворота.** Все модули меняют систему
только через функции `run()` и `run_write()`: они показывают команду или diff
до выполнения, спрашивают подтверждение, делают резервную копию файла и пишут
в лог. Обойти их нельзя — прямой вызов `apt-get` или `sed -i` в модуле роняет
сборку (`tests/lint-run-guard.sh`).

## Манифест

Единственный файл, который ты правишь руками — `manifest/host.json`. Это JSON,
но **с комментариями**: строка после `#` игнорируется.

```jsonc
{
  "host": {
    # Уберёшь этот ключ — keel не тронет репозитории вообще
    "repos": "no-subscription"
  },
  "guests": []
}
```

Читается модулем `JSON::PP`, который входит в стандартную поставку Perl, — а
Perl есть на любом Proxmox. Значит манифест читается всегда: без интернета,
без `apt install`, на полумёртвой системе. Справочник полей:
[docs/MANIFEST.md](docs/MANIFEST.md).

## Восстановление с нуля

Главный документ проекта — [docs/00-RECOVERY.md](docs/00-RECOVERY.md):
пошаговый путь от чистого железа до работающего хоста с гостями, включая то,
чего keel не восстановит (данные внутри гостей, пароли, разметку дисков,
настройки BIOS).

## Разработка

```bash
./tests/run.sh             # все проверки, прямо здесь
./tests/run.sh config      # только те, где в названии есть "config"

./tests/docker.sh          # то же самое в Debian 13 — основе Proxmox VE 9
./tests/docker.sh --shell  # интерактивная оболочка в том же окружении
```

Тесты нарочно без bats: проект обещает работать на голом Proxmox, и его
собственные тесты держатся того же правила. Нужен только bash.

Контейнер нужен не для изоляции, а ради проверки допущений: Debian 13 —
это то, на чём стоит Proxmox VE 9, и именно там видно, есть ли `perl` с
`JSON::PP`, работает ли режим `relaxed` (ради него и выбран JSON вместо
YAML) и стоит ли `whiptail` из коробки. Первая группа тестов —
«Окружение» — отвечает ровно на эти вопросы.

Настоящие `qm`, `pct`, `pvesm`, `pvesh` в тестах подменяются заглушками,
которые записывают свои аргументы: так проверяется сборка команд — место,
где живёт большинство ошибок. Модули работают против временного каталога
(`KEEL_FS_ROOT`), живая система при этом не страдает, и на это есть
отдельный тест.
