# Туннель Cloudflare

Туннель пускает твои сервисы наружу без открытых портов, белого IP и проброса
на роутере. `cloudflared` внутри контейнера сам соединяется с Cloudflare
изнутри — на роутере менять не нужно ничего.

Что делает keel и чего не делает:

| | |
|---|---|
| Создать контейнер, поставить `cloudflared`, подключить его к туннелю | **keel** |
| Создать туннель, выдать токен, привязать адрес к сервису | **ты, в панели Cloudflare** |

Причина простая: всё, что делается в панели, требует входа через браузер.
Автоматизировать это честно нельзя, поэтому здесь — инструкция.

---

## Почему в контейнере, а не на хосте

Хост Proxmox — это фундамент. Чем меньше на нём постороннего, тем меньше
поводов ему сломаться и тем проще собрать его заново. Туннель в контейнере:

- на хост не ставится ни одного пакета и не добавляется ни одного репозитория;
- туннель описан в манифесте как обычный гость и поднимается сам при сборке
  хоста с нуля — вместе со всем остальным;
- если туннель понадобится перенести или пересоздать, это отдельный
  контейнер, а не операция на живом хосте.

Контейнеру нужен только исходящий доступ в сеть. Входящих портов у него нет.

---

## Шаг 1. Создать туннель в панели Cloudflare

Нужен домен, добавленный в Cloudflare (бесплатного тарифа хватает).

1. Открой [one.dash.cloudflare.com](https://one.dash.cloudflare.com/) →
   **Networks** → **Tunnels** → **Create a tunnel**.
2. Тип — **Cloudflared**. Дай туннелю имя, например `home`.
3. На шаге «Install and run a connector» покажут команду установки. Целиком
   она не нужна — нужен **только токен**: длинная строка после
   `--token`, начинается с `eyJhIjoi`.
4. Скопируй токен. Это пароль от туннеля: кто им владеет, тот может выдать
   себя за твой туннель.

## Шаг 2. Описать туннель в манифесте

```jsonc
{
  "id": 102,
  "name": "tunnel",
  "profile": "cloudflared",
  "storage": "local-lvm",
  "bridge": "vmbr0",
  "start_on_boot": true
}
```

Больше ничего не нужно: размеры (1 ядро, 512 МБ, 4 ГБ) берутся из профиля.

**Токена в манифесте нет и не будет.** Манифест — обычный текстовый файл,
который удобно копировать и хранить в git; секретам там не место.

## Шаг 3. Применить

```bash
keel apply --only guests/50-guests
```

keel спросит токен и сохранит его в `/root/keel/secrets/cloudflared.txt` с
правами 0600. На экране вместо токена будут звёздочки — и в логе тоже.

Посмотреть сохранённый токен потом:

```bash
keel token
```

Если запускаешь без вопросов (`--yes`), положи токен заранее:

```bash
install -m 600 /dev/null /root/keel/secrets/cloudflared.txt
nano /root/keel/secrets/cloudflared.txt     # одной строкой, без пробелов
```

Без токена keel честно откажется создавать контейнер. Придумать токен он не
может, а поднять туннель, который никуда не подключён, — значит соврать.

## Шаг 4. Привязать адреса к сервисам

Контейнер поднялся, в панели Cloudflare туннель стал зелёным. Теперь укажи,
что за чем стоит: **Tunnels** → твой туннель → **Configure** → **Public
Hostname** → **Add a public hostname**.

| Поле | Пример |
|---|---|
| Subdomain | `ha` |
| Domain | `твой-домен.ru` |
| Service → Type | `HTTP` |
| Service → URL | `<адрес гостя>:8123` — например, тот, что Proxmox показывает на вкладке ВМ |

Адрес — это IP **гостя**, а не контейнера с туннелем: туннель ходит до
сервиса по локальной сети. Узнать адрес гостя:

```bash
pct exec 102 -- hostname -I      # адрес самого туннеля
qm guest cmd 100 network-get-interfaces   # адрес ВМ, если агент установлен
```

Проще всего смотреть в веб-интерфейсе Proxmox, на вкладке гостя.

После сохранения `https://ha.твой-домен.ru` работает из любой точки мира.

## Проверить, что живо

```bash
pct exec 102 -- systemctl is-active cloudflared     # active
pct exec 102 -- cloudflared tunnel info             # состояние соединений
pct exec 102 -- journalctl -u cloudflared -n 50     # если что-то не так
```

В панели Cloudflare у туннеля должен гореть статус **Healthy**.

---

## Если туннель не поднялся

**Статус Down, в журнале `Unauthorized`.** Токен неверный или от другого
туннеля. Удали файл и повтори:

```bash
rm /root/keel/secrets/cloudflared.txt
keel apply --only guests/50-guests
```

**Служба не запускается, `cloudflared: command not found`.** Не скачался
пакет — у контейнера нет доступа в интернет. Проверь сеть:

```bash
pct exec 102 -- ping -c1 1.1.1.1
pct exec 102 -- getent hosts github.com
```

**Туннель зелёный, но адрес отдаёт 502.** Туннель жив, а сервис за ним — нет.
Ошибка в Service URL: неверный IP гостя, неверный порт или сервис не слушает
на внешнем интерфейсе. Проверь изнутри контейнера с туннелем:

```bash
pct exec 102 -- curl -sS -o /dev/null -w '%{http_code}\n' http://<адрес-гостя>:8123
```

---

## Восстановление после переустановки хоста

Туннель восстанавливается как любой другой гость — `keel apply`. Понадобится
только токен: он в `/root/keel/secrets/`, а этот каталог **не попадает** ни в
git, ни в архив конфигурации keel. Держи копию токена там же, где хранишь
остальные пароли.

Настройки адресов остались в панели Cloudflare и переустановку хоста
переживают сами: как только новый контейнер подключится с тем же токеном,
всё заработает без единой правки на стороне Cloudflare.
