# Восстановление хоста с нуля

Этот документ написан для того дня, когда хост не загрузился, диск умер или
ты переезжаешь на новое железо. Читать сверху вниз, не пропуская.

Ориентир по времени: около часа, из которых почти всё — ожидание установщика
и скачивание образов.

**Интернет нужен.** Без него не скачать ни образы гостей, ни пакеты, ни сам
keel — восстанавливать будет попросту нечего. Если сеть на хосте не поднялась,
сначала чини сеть.

---

## Что нужно иметь под рукой

| Что | Где взять, если потерялось |
|---|---|
| Этот репозиторий | GitHub. Если и его нет — архив конфигурации, см. ниже |
| `manifest/host.json` | внутри архива `keel-host-*.tar.gz`, файл `manifest.json` |
| Флешка с ISO Proxmox VE | [proxmox.com/downloads](https://www.proxmox.com/downloads) |
| Твой SSH-ключ | оттуда, где ты его хранишь: менеджер паролей, другой компьютер |
| Архив `keel-host-*.tar.gz` | то место, куда ты его складывал (не этот хост!) |

Если архива конфигурации нет — ничего страшного, хост соберётся из манифеста.
Архив нужен, чтобы подсмотреть **точные** сетевые настройки, разметку дисков
и список гостей, которые были до аварии.

---

## Шаг 1. Поставить Proxmox VE

Обычная установка с флешки. Подробности и вариант с автоустановкой —
[docs/20-install-pve.md](20-install-pve.md).

На что обратить внимание в установщике:

- **Файловая система.** Была ZFS — выбирай ZFS, иначе диски со старыми данными
  могут не подхватиться. Точные названия смотри в `host-report.txt` из архива.
- **Имя хоста и IP.** Задай те же, что были. Иначе гости с фиксированными
  адресами и все закладки в браузере перестанут работать.
- **Пароль root.** Задай новый, старый всё равно нигде не хранится.

После установки проверь, что веб-интерфейс открывается: `https://<ip>:8006`.

---

## Шаг 2. Поставить keel

Через SSH или прямо в консоли хоста:

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/vshivtsev-dev/keel/main/install.sh)"
```

Что произойдёт: репозиторий ляжет в `/opt/keel`, команда `keel` станет
доступной, из примера создастся `manifest/host.json`. Система при этом
**не меняется** — ни одной настройки без твоего подтверждения.

---

## Шаг 3. Вернуть манифест

Манифест — это описание того, каким хост должен быть. Без него keel ничего не
сделает (правило нуля), поэтому сначала верни его.

**Если репозиторий с твоим манифестом в git:**

```bash
cd /opt/keel && git pull
cp manifest/host.json.твоя-копия manifest/host.json   # если хранишь отдельно
```

**Если есть архив конфигурации:**

```bash
mkdir -p /tmp/восстановление && cd /tmp/восстановление
tar -xzf /путь/к/keel-host-2026-09-15_030000.tar.gz
cp manifest.json /opt/keel/manifest/host.json
less host-report.txt        # ← здесь вся картина прежнего хоста
```

`host-report.txt` — самое ценное в архиве. Там версия Proxmox, разметка
дисков, список хранилищ, сетевые адреса, перечень всех гостей и состояние
загрузчика. По нему сверяешь, всё ли совпало.

**Если нет ни того, ни другого:** возьми `manifest/host.example.json` и опиши
хост заново. Справочник полей — [docs/MANIFEST.md](MANIFEST.md).

---

## Шаг 4. Посмотреть, что за машина

```bash
keel doctor
```

Только чтение, ничего не меняет. Сверь с `host-report.txt`:

- версия Proxmox и Debian;
- хранилища на месте, имена совпадают;
- сетевой мост называется так же, как раньше;
- видеокарта видна, `/dev/dri` есть (если планируется рабочий стол);
- манифест читается без ошибок.

Расхождения лучше устранить сейчас. Особенно имена хранилищ: если старые
гости лежали на `local-lvm`, а новый установщик завёл `local-zfs`, поправь
манифест — иначе keel создаст гостей не там.

---

## Шаг 5. Посмотреть план

```bash
keel plan
```

Выводится точный список того, что произойдёт. **Ни одна команда пока не
выполняется.** Прочитай его целиком. Если что-то выглядит неожиданно —
разбирайся сейчас, а не после.

---

## Шаг 6. Применить

```bash
keel apply
```

Перед каждым изменением keel показывает команду или diff и спрашивает:
применить, пропустить или прервать. Если план уже прочитан и вопросов нет:

```bash
keel apply --yes
```

Порядок такой: репозитории → обновления → хранилища → расписание бэкапов →
гости → копия конфигурации. Гости создаются последними, когда хранилища уже
на месте.

Скачивание образов идёт долго (HAOS — около 400 МБ, облачные образы Ubuntu и
Debian — 300–600 МБ). Образы кэшируются в `/var/lib/keel/images`, при
повторных запусках качаться заново не будут.

---

## Шаг 7. Вернуть данные гостей

Тут keel заканчивается и начинается vzdump. **keel создаёт гостей пустыми** —
он знает, какими они должны быть, но не хранит их содержимое.

Если есть бэкапы виртуалок:

```bash
# посмотреть, что есть
pvesm list local | grep vzdump

# восстановить конкретного гостя
qmrestore /var/lib/vz/dump/vzdump-qemu-100-*.vma.zst 100     # виртуальная машина
pct restore 102 /var/lib/vz/dump/vzdump-lxc-102-*.tar.zst    # контейнер
```

Восстановление из бэкапа **заменяет** гостя целиком. Если keel уже создал
пустого гостя с этим id — удали его перед восстановлением или используй
свободный id.

Логика простая: **есть бэкап гостя — восстанавливай из бэкапа, нет — keel
создаст нового по манифесту.** Для Home Assistant это обычно бэкап vzdump
плюс собственный бэкап Home Assistant внутри.

---

## Шаг 8. Проверить, что всё сошлось

```bash
keel verify     # соответствует ли хост манифесту
keel doctor     # общее состояние
```

Руками стоит проверить:

- [ ] веб-интерфейс открывается по привычному адресу;
- [ ] гости запускаются и получают сеть;
- [ ] задание резервного копирования видно в Датацентр → Резервные копии;
- [ ] свежая копия конфигурации появилась в каталоге из манифеста;
- [ ] вход по SSH ключом работает;
- [ ] рабочий стол принимает подключение (RDP для контейнера, SPICE для ВМ).

## Чего keel не восстановит

Честный список — чтобы не было сюрпризов:

**Данные внутри гостей.** Это работа vzdump и бэкапов самих приложений.

**Пароли.** В манифесте их нет и не будет. Пароли рабочих столов лежат в
`/var/lib/keel/secrets/` — этот каталог не в git и в архив конфигурации не
попадает. Храни их в менеджере паролей.

**Разметку дисков и ZFS-пулы.** Создание пулов — слишком разрушительная
операция, чтобы её автоматизировать. `host-report.txt` подскажет, как было.

**Настройки BIOS.** Виртуализация, IOMMU, порядок загрузки, Above 4G —
только руками. См. [docs/10-hardware-bios.md](10-hardware-bios.md).

**Сетевую конфигурацию.** Установщик Proxmox создаёт рабочий `vmbr0` сам;
сложную сеть (VLAN, бонды) восстанавливай из `etc/network/interfaces` в
архиве. Почему это не автоматизировано — [docs/BACKLOG.md](BACKLOG.md).

## Если что-то пошло не так

```bash
keel logs                       # полный лог последнего запуска
ls /var/lib/keel/backups/       # копии файлов, снятые до каждой правки
```

Перед любой правкой файла keel кладёт его копию в
`/var/lib/keel/backups/<дата>/<путь>`. Вернуть как было — обычный `cp`.

Частые случаи — [docs/90-troubleshooting.md](90-troubleshooting.md).
