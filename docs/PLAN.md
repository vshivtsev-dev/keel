# Архитектура и дорожная карта

## Задача

Переустановил Proxmox с нуля или потерял бэкап — нужно быстро и понятно
вернуть хост и несколько базовых ВМ. Без вспоминания, что и где было настроено.

## Почему не взяли готовое

| Проект | Что взяли | Почему не подошёл целиком |
|---|---|---|
| [community-scripts/ProxmoxVE](https://github.com/community-scripts/ProxmoxVE) | модель «одна команда → меню → готовый гость», общая библиотека функций | логика качается из интернета при каждом запуске; нет описания желаемого состояния — только разовые действия |
| [ProxMenux](https://github.com/MacRimi/ProxMenux) | доказательство, что приятный UX на голом PVE вообще возможен | разросся до веб-дашборда и systemd-сервиса; GPL-3 |
| Ansible-роли для PVE | идея декларативности и идемпотентности | нужен Ansible на хосте или подготовленная рабочая станция |
| Terraform / OpenTofu (bpg) | «манифест как источник правды», план как артефакт | state-файл, который тоже можно потерять; для нескольких гостей оверинжиниринг |
| [Автоустановка PVE (`answer.toml`)](https://pve.proxmox.com/wiki/Automated_Installation) | закрывает шаг «до того, как хост существует» | требует другой машины для сборки ISO — отдельный трек, в документацию |

Середина между ними: декларативный манифест, идемпотентные провайдеры, план
как сохранённый артефакт и экран, на котором всё это видно сразу.

Состояние keel не хранит нигде, и это принципиально: источник правды — сам
хост, а манифест говорит, каким он должен быть. Терять нечего.

## Слои

```
  ┌──────────────────────────────────────────────────────────────┐
  │  СЛОЙ 4. Интерфейс   internal/ui, internal/cli               │
  │  экран, и те же действия командами:                          │
  │  keel plan / apply / verify / doctor                         │
  └───────────────────────────┬──────────────────────────────────┘
                              │ читает
  ┌───────────────────────────▼──────────────────────────────────┐
  │  СЛОЙ 3. Манифест  /root/keel/host.json                      │
  │  ЧТО должно быть. Единственный файл, который правишь руками. │
  └───────────────────────────┬──────────────────────────────────┘
                              │ передаёт значения
  ┌───────────────────────────▼──────────────────────────────────┐
  │  СЛОЙ 2. Провайдеры  internal/provider/…                     │
  │  КАК это сделать. Один провайдер = одна область.             │
  │  Контракт: Configured / Plan / Verify. Ничего не выполняет.  │
  └───────────────────────────┬──────────────────────────────────┘
                              │ опирается на
  ┌───────────────────────────▼──────────────────────────────────┐
  │  СЛОЙ 1. Ядро  internal/{facts,exec,plan,engine,secret}      │
  │  факты о хосте (только чтение), ворота изменений, план       │
  │  как данные, движок, секреты, журнал                         │
  └──────────────────────────────────────────────────────────────┘
```

Смысл разделения: правишь только Слой 3, а Слои 1–2 читаешь редко — и когда
читаешь, видишь короткие файлы, а не километровый скрипт.

Граница между слоями 1 и 2 жёсткая: провайдер не ходит в файловую систему и
не запускает команд. Из-за этого он проверяется без хоста, без сети и без
root — обычными тестами.

## Принятые решения

**Один статический бинарник, без зависимостей.** Инструмент восстановления,
который перед работой требует `apt install`, — плохой инструмент
восстановления. Поэтому keel не требует ничего: ни `perl`, ни `whiptail`, ни
даже совместимой libc (`CGO_ENABLED=0`, 7 МБ).

Сначала это правило привело к bash: всё нужное есть на чистом Proxmox. Потом
оно же увело от bash — статический бинарник зависит от системы ещё меньше.
Почему и как — [PORT.md](PORT.md).

**Манифест в JSON с комментариями.** Человек правит его руками, и
комментарий рядом с ключом полезнее отдельного документа, до которого ещё
надо дойти. YAML потребовал бы разбора куда сложнее при том же результате.

Формат — JWCC: `//`, `/* */` и висячие запятые, разбирает `hujson`.
Комментарии `#` работали, пока манифест читался через `JSON::PP` с его
режимом `relaxed`; их поддержка стоила своего препроцессора на полтораста
строк ради одного знака, и от неё отказались. На такой манифест keel
отвечает не «invalid character», а подсказкой заменить `#` на `//`.

**Запуск на самом хосте, одной командой.** Рабочей станции при восстановлении
может не быть.

**Свои модули, чужие каталоги.** Логика — наша. Отдельным пунктом меню (Фаза 5)
можно будет запустить community-scripts для разовой установки приложений в LXC,
с явной пометкой «вне манифеста, автоматически не восстановится».

## Графика для десктопной машины

Железо: Radeon 780M в APU Ryzen 7 8745HS — **единственная видеокарта в машине**.

| | **A. LXC + /dev/dri** | **B. ВМ + virtio-gl** | **C. ВМ + полный проброс** |
|---|---|---|---|
| 3D (OpenGL) | ~нативно | грубо 20–50% | 95–99% |
| Vulkan | да | нет | да |
| Аппаратное декодирование видео | да | нет, декод на CPU | да |
| Изоляция | общее ядро с хостом | полная | полная |
| Хост теряет монитор | нет | нет | **да, навсегда** |
| Риск для хоста | низкий | низкий | высокий |
| Откат | мгновенный | мгновенный | правка загрузчика + перезагрузка |
| Сложность | средняя | низкая | высокая |

Цифры — порядки величин из общей литературы, а не замеры этой машины.

**Выбрано: A (LXC + /dev/dri) как основной путь.** Даёт аппаратный доступ к
видеокарте без потери консоли хоста и без reset bug, известного именно для
780M. B остаётся доступным вариантом для случая, когда нужна настоящая ВМ.

C тоже реализован — по прямой просьбе и с полным набором предохранителей:
проверки до изменений, подтверждение с набором адреса устройства, запись
всех правок и откат одной командой. По умолчанию выключен.

## Проверено и не проверено

Всё, что можно проверить без живого Proxmox, проверено: разбор манифеста,
логика провайдеров, сборка команд (тесты сверяют их дословно), сборка архива
конфигурации, поведение при отсутствии манифеста, отрисовка экрана в обеих
раскладках, установка и обновление со сверкой контрольной суммы.

Не проверено на настоящем хосте: сами вызовы Proxmox. Команды написаны по
документации и отчётам, но не выполнялись на живой системе. Поэтому режим
пошагового подтверждения — по умолчанию, а `keel plan --commands` показывает
всё до единой команды заранее.

## Границы

keel — инструмент восстановления, а не система управления. Всё для
повседневной работы живёт в веб-интерфейсе Proxmox. Веб-дашборда у keel не
будет.
