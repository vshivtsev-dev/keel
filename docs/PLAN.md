# Архитектура и дорожная карта

## Задача

Переустановил Proxmox с нуля или потерял бэкап — нужно быстро и понятно
вернуть хост и несколько базовых ВМ. Без вспоминания, что и где было настроено.

## Почему не взяли готовое

| Проект | Что взяли | Почему не подошёл целиком |
|---|---|---|
| [community-scripts/ProxmoxVE](https://github.com/community-scripts/ProxmoxVE) | модель «одна команда → меню → готовый гость», общая библиотека функций | логика качается из интернета при каждом запуске; нет описания желаемого состояния — только разовые действия |
| [ProxMenux](https://github.com/MacRimi/ProxMenux) | доказательство, что голый bash даёт приятный UX на чистом PVE | разросся до веб-дашборда и systemd-сервиса; GPL-3 |
| Ansible-роли для PVE | идея декларативности и идемпотентности | нужен Ansible на хосте или подготовленная рабочая станция |
| Terraform / OpenTofu (bpg) | «манифест как источник правды» | state-файл, который тоже можно потерять; для нескольких гостей оверинжиниринг |
| [Автоустановка PVE (`answer.toml`)](https://pve.proxmox.com/wiki/Automated_Installation) | закрывает шаг «до того, как хост существует» | требует другой машины для сборки ISO — отдельный трек, в документацию |

Середина между ними: декларативный манифест + идемпотентные bash-модули +
меню, и всё лежит локально в git.

Смысл разделения: правишь только Слой 3, а Слои 1–2 читаешь редко — и когда
читаешь, видишь короткие файлы, а не километровый скрипт.

## Принятые решения

**Голый bash, без зависимостей.** Всё нужное есть на чистом Proxmox.
Инструмент восстановления, который перед работой требует `apt install`, —
плохой инструмент восстановления. Из этого же следует отказ от `gum`, `fzf`
и прочих красивых рисовалок: за каждой стоит бинарник, которого на голом
хосте нет.

**Манифест в JSON с комментариями.** Читается `JSON::PP` из стандартной
поставки Perl, который на Proxmox есть всегда (сам PVE написан на Perl).
Режим `relaxed` даёт комментарии `#` и висячие запятые. YAML потребовал бы
либо вендоренного бинарника `yq` на 12 МБ, либо парсера, которого может не
оказаться.

**Запуск на самом хосте, одной командой.** Рабочей станции при восстановлении
может не быть.

**Свои модули, чужие каталоги.** Логика — наша. Отдельным пунктом меню (Фаза 5)
можно будет запустить community-scripts для разовой установки приложений в LXC,
с явной пометкой «вне манифеста, автоматически не восстановится».

**Один вопрос на план, а не вопрос на команду.** Сначала keel спрашивал перед
каждым изменением, отдельным окном whiptail. На пяти командах это выглядело
разумно; на примерном манифесте с тремя гостями команд тридцать
(`keel apply --dry-run | grep -c '^→'`), и каждое окно затирает экран — к
десятому вопросу уже не видно, что сделано. Теперь весь список показывается
заранее, согласие берётся один раз, и дальше работа идёт сплошным потоком,
как у `apt` и `terraform`.

Гарантия при этом не ослабла, а переехала: до первого изменения человек видит
не обрезанный до четырнадцати строк diff в окне, а весь план целиком, и может
развернуть его до каждой команды (ответ `d`). Пошаговый режим остался под
`--step` — для случаев, когда хочется держать руку на рубильнике.

**Интерфейс — текст, окон нет вообще.** Сначала whiptail оставили для меню и
списков с галочками. Не прижилось, и причины измеримые. Newt заливает своим
фоном весь экран: в дампе терминала 160×45 это `ESC[45m` на каждой из сорока
пяти строк. Поверх заливки он рисует коробку шириной ровно 78 колонок и
высотой не больше 30 строк — то есть на широком терминале половина экрана
уходит под пустой фон вокруг узкой колонки текста, и ни один из трёх
параметров от размера терминала не зависит.

Текст этих проблем не имеет по построению: занимает всю доступную ширину,
ничего не заливает, прокручивается штатной прокруткой и копируется мышью.
Важнее другое: экран больше не перерисовывается, поэтому всё сказанное
раньше остаётся выше по прокрутке. Для инструмента восстановления, который
смотрят через IPMI-консоль, это разница между «видно ход работы» и «видно
последний кадр». Заодно исчезла пауза «нажми любую клавишу» — она была
нужна только затем, чтобы окно не затёрло вывод.

Цена: по списку больше не ходят стрелками, пункт выбирается номером. Размен
сознательный. Пропал и целый класс расхождений: каждая функция интерфейса
имела две реализации, оконную и текстовую, и текстовая как менее заметная
отставала — в ней, например, Enter на списке гостей значил «никого», тогда
как в окне та же клавиша означала «отмеченных». За возвратом рисовалки
следит `tests/run.sh`, проверка «статика: интерфейс не рисует окон».

## Графика для десктопной машины

Железо: Radeon 780M в APU Ryzen 7 8745HS — **единственная видеокарта в машине**.

| | **A. LXC + /dev/dri** | **B. ВМ + virtio-gl** | **C. ВМ + полный проброс** |
|---|---|---|---|
| 3D (OpenGL) | ~нативно | грубо 20–50% | 95–99% |
| Vulkan | да | нет | да |
| Аппаратное декодирование видео | да | нет, декод на CPU | да |
| Изоляция | общее ядро с хостом | полная | полная |
| Хост теряет монитор | нет | нет | **да, навсегда** |
| Риск для хоста | низкий | низкий | высокий |
| Откат | мгновенный | мгновенный | правка загрузчика + перезагрузка |
| Сложность | средняя | низкая | высокая |

Цифры — порядки величин из общей литературы, а не замеры этой машины.

**Выбрано: A (LXC + /dev/dri) как основной путь.** Даёт аппаратный доступ к
видеокарте без потери консоли хоста и без reset bug, известного именно для
780M. B остаётся доступным вариантом для случая, когда нужна настоящая ВМ.

C тоже реализован — по прямой просьбе и с полным набором предохранителей:
проверки до изменений, подтверждение с набором адреса устройства, запись
всех правок и откат одной командой. По умолчанию выключен.

## Проверено и не проверено

Всё, что можно проверить без живого Proxmox, проверено: разбор манифеста,
логика модулей, сборка команд (подставные `qm`, `pct`, `pvesm`, `pvesh`
записывают аргументы, и тесты сверяют их дословно), сборка архива
конфигурации, поведение при отсутствии манифеста.

Не проверено на настоящем хосте: сами вызовы Proxmox. Команды написаны по
документации и отчётам, но не выполнялись на живой системе. Поэтому `keel plan`
показывает всё до единой команды заранее, а `keel apply` не делает ни одного
изменения, не показав весь список и не спросив.

## Границы

keel — инструмент восстановления, а не система управления. Всё для
повседневной работы живёт в веб-интерфейсе Proxmox. Веб-дашборда у keel не
будет.

Отдельно про **контейнер с веб-интерфейсом** — эту мысль обсуждали и
отклонили, причины стоит записать, чтобы не возвращаться:

1. **Курица и яйцо.** keel восстанавливает голый хост. В этот момент нет ни
   docker, ни LXC, ни гостей — их-то он и создаёт. Инструмент восстановления
   не может требовать контейнер, чтобы запуститься.
2. **Права.** Чтобы менять хост из контейнера, нужен либо привилегированный
   контейнер с корнем хоста, либо SSH обратно на хост. И то и другое
   пробивает дыру в схеме «всё идёт через `run()`, всё логируется, всё с
   резервной копией файла».
3. **Дублирование.** Повседневность уже закрыта веб-интерфейсом Proxmox.

Веб-морда **на самом хосте** этих возражений не вызывает, и она сделана:
`keel web`, см. [docs/50-web.md](50-web.md). Это надстройка над тем же
планом, а не замена терминалу, и граница проходит там же, где раньше:

* страница не содержит логики о хосте — только «покажи» и «применяй»;
* согласие берётся так же, как в терминале: сперва план, потом кнопка;
* восстановление с нуля остаётся терминальным, потому что до установленного
  Proxmox HTTP-сервер запускать негде.

Дашбордом при этом keel не стал: там нет ни графиков, ни состояния гостей в
реальном времени, ни управления виртуалками. Всё это уже есть в веб-интерфейсе
Proxmox, и дублировать его keel не собирается.
