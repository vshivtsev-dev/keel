# Пошаговое тестирование

Порядок здесь не случайный: от «ничего не может сломаться» к «меняет систему»,
и внутри — от самого безобидного изменения к самому заметному. На каждом шаге
есть **независимая проверка** — не «keel сказал, что получилось», а команда
Proxmox, которая показывает результат сама.

Проходить сверху вниз. Если шаг не прошёл — остановись и пришли то, что
указано в конце этого файла; следующие шаги опираются на предыдущие.

---

## Перед началом

**Где тестировать.** Идеально — на машине, которую не жалко переустановить.
Если такой нет, первый же реальный шаг (шаг 5) делает архив конфигурации —
это и будет точка возврата.

**Чем откатывать.** Перед каждой правкой файла keel кладёт его копию в
`/root/keel/backups/<дата>/<путь>`. Вернуть — обычный `cp`. Это работает
независимо от того, дошёл keel до конца или свалился на середине.

**Чего keel не делает ни на одном шаге:** не удаляет гостей, не трогает то,
чего нет в манифесте, не перезагружает хост.

`relaxed`, `whiptail`). **Это первое, чего я не проверял** — сборка образа
в песочнице была недоступна.

- [ ] тесты прошли в docker (если он есть)

## Шаг 1. Установка на хост

Одна команда, под root:

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/vshivtsev-dev/keel/main/install.sh)"
```

Ни git, ни токенов, ни копирования файлов: установщик скачивает архив ветки
`main` через curl и распаковывает в `/root/keel/app`. Систему он при этом не
настраивает — только кладёт код и делает команду `keel` доступной.

Всё, с чем работаешь ты, оказывается в одном каталоге:

```
/root/keel/
  host.json     манифест: единственный файл, который ты правишь
  secrets/      пароли гостей и токены
  backups/      копии файлов до того, как keel их правил
  logs/         логи запусков
  images/       кэш скачанных образов
  journal.tsv   что и когда применялось
  app/          код keel — перезаписывается при обновлении
```

Обновление потом — повторный запуск той же команды. Твой `host.json` при этом
не затирается: он лежит вне каталога с кодом.

**Если keel уже стоял** версии 0.1.0, установщик сам перенесёт данные со
старых мест (`/var/lib/keel`, `/var/log/keel`, манифест из `/opt/keel`) и
скажет, что перенёс. Старый каталог с кодом он не удаляет — напечатает
команду, а решение за тобой.

Независимая проверка:

```bash
keel version     # должно напечатать keel 0.2.0
keel modules     # шесть модулей
ls /root/keel    # host.json, app/ и данные рядом
ls /var/lib/keel # должно уже не существовать
```

- [ ] установка прошла одной командой
- [ ] `keel version` печатает 0.2.0
- [ ] `keel modules` показывает шесть модулей
- [ ] данные переехали: `/root/keel/host.json` на месте, `/var/lib/keel` нет
- [ ] пароль прежнего гостя находится: `keel password 201`

## Шаг 3. Манифест под твой хост

Открой `/root/keel/host.json` и приведи в соответствие с тем, что
показал `doctor`. Самое частое расхождение — имя хранилища: установщик

```

sed -i 's/"host"/"hosts"/' /root/keel/host.json

sed -i 's/"hosts"/"host"/' /root/keel/host.json
```

## Шаг 5. Первое настоящее изменение: архив конфигурации

Почему именно он первым: модуль только создаёт архив, ничего в системе не
меняет — и сразу даёт точку возврата для всех следующих шагов.

```bash
keel apply --only host/90-config-backup
```

keel покажет команду и спросит подтверждение. Отвечай «Применить».

Независимая проверка:

```bash
ls -lh /var/lib/vz/dump/keel-config/
tar -tzf /var/lib/vz/dump/keel-config/keel-host-*.tar.gz | head -20
tar -xzOf /var/lib/vz/dump/keel-config/keel-host-*.tar.gz ./host-report.txt | head -40
```

В архиве должны быть `etc/pve/`, `etc/network/interfaces`, `host-report.txt`
и `manifest.json`.

**Скопируй архив с хоста куда-нибудь ещё.** Копия рядом с оригиналом спасает
только от опечаток.

Проверь идемпотентность — повторный запуск не должен делать новый архив:

```bash
keel apply --only host/90-config-backup    # должно сказать «уже в нужном состоянии»
```

- [ ] архив создан и содержит `etc/pve`
- [ ] `host-report.txt` читается и содержит версии, диски, список гостей
- [ ] архив скопирован с хоста
- [ ] повторный запуск ничего не делает

## Шаг 6. Репозитории

Первое изменение, которое реально правит систему. Откат тривиален.

```bash
keel apply --only host/10-repos
```

Перед записью файла keel покажет diff. Посмотри на него: пути, кодовое имя
(`trixie` для PVE 9, `bookworm` для PVE 8), формат.

Независимая проверка:

```bash
cat /etc/apt/sources.list.d/pve-no-subscription.sources   # или .list на PVE 8
cat /etc/apt/sources.list.d/pve-enterprise.sources       # смотри целиком, не только Enabled
apt-get update     # должно пройти без 401 и без «Malformed stanza»
```

В выключенном файле формата deb822 **не должно быть пустой строки** перед
`Enabled: false`. Пустая строка начинает новую запись, у записи не оказывается
поля `Types`, и apt объявляет битым весь файл — а вместе с ним перестаёт
читать и все остальные источники. Первая версия keel делала именно так; если
твой хост это застал, свежая версия чинит файл сама при следующем применении.


Откат, если что-то не так:

```bash
ls /root/keel/backups/
cp /root/keel/backups/<дата>/etc/apt/sources.list.d/* /etc/apt/sources.list.d/
```

- [ ] `apt-get update` проходит без ошибки 401 и без `Malformed stanza`
- [ ] enterprise-репозиторий помечен выключенным, но не удалён
- [ ] в выключенном `.sources` нет пустых строк
- [ ] `keel verify --only host/10-repos` подтверждает результат

## Шаг 8. Хранилища

```bash
keel apply --only host/30-storage
```

Независимая проверка:

```bash
pvesm status
grep -A5 'dir: local' /etc/pve/storage.cfg    # в content должны появиться snippets
```

`snippets` обязательны — без них не создать ВМ из облачного образа.

Модуль только **добавляет** типы content: то, что было у хранилища до keel,
остаётся на месте. Если на хосте когда-то стояла версия keel, затиравшая
набор целиком, сверься со списком — на PVE 9 у `local` по умолчанию есть ещё
и `import` (панель импорта дисков и OVA). Вернуть:

```bash
pvesm set local --content backup,import,iso,snippets,vztmpl
```

- [ ] `snippets` появились в content хранилища `local`
- [ ] прежние типы content никуда не делись
- [ ] остальные хранилища не тронуты
- [ ] `pvesm status` показывает всё как раньше

## Шаг 10. Первый гость: Home Assistant OS

Самый большой шаг. Скачивание образа — около 400 МБ.

```bash
keel apply --only guests/50-guests
```

На что смотреть по дороге:

1. определилась ли версия HAOS через GitHub (или взялась запасная);
2. идёт ли прогресс скачивания на экране;
3. проходит ли `qm set --scsi0 ...,import-from=...` — **это место, в котором
   я меньше всего уверен**.

Независимая проверка:

```bash
qm config 200
qm status 200
ls -lh /root/keel/images/           # образ осел в кэше
```

В `qm config 200` проверь: `bios: ovmf`, `machine: q35`, есть `efidisk0`,
`scsi0` указывает на диск нужного размера, `boot: order=scsi0`.

Открой консоль ВМ в веб-интерфейсе — Home Assistant должен загрузиться и
показать адрес.

Проверь главное правило — существующий гость не трогается:

```bash
keel apply --only guests/50-guests     # «200 «haos» уже существует — пропускаю»
```

И сообщение о расхождении: поменяй в манифесте `memory` у гостя 200 и
запусти `keel plan` — keel должен сказать, что память отличается, но ничего
не исправить.

## Шаг 11. Рабочий стол в контейнере

Самый сложный кусок: шаблон, проброс видеокарты, установка XFCE и xrdp
внутри.

```bash
keel apply --only guests/50-guests
```

keel спросит пароль для пользователя рабочего стола. Оставишь пустым —
сгенерирует и сохранит; посмотреть потом: `keel password 201`.

Независимая проверка:

```bash
pct config 201                    # должны быть dev0/dev1 с /dev/dri
pct exec 201 -- ls -l /dev/dri    # устройства видны внутри
pct exec 201 -- id av           # пользователь в группах video/render
pct exec 201 -- systemctl status xrdp
```

Ускорение — главная цель варианта с контейнером:

```bash
pct exec 201 -- glxinfo -B | grep "OpenGL renderer"   # должен быть AMD, не llvmpipe
pct exec 201 -- vainfo                                 # профили аппаратного декода
```

`llvmpipe` означает, что видеокарта до контейнера не доехала.

Подключись RDP-клиентом на адрес контейнера, пользователем из манифеста.
Проверь: открывается рабочий стол, работает браузер, VLC играет видео со
звуком.

- [ ] контейнер создан, `/dev/dri` внутри виден
- [ ] `glxinfo` показывает AMD, а не llvmpipe
- [ ] `vainfo` выдаёт список профилей
- [ ] RDP подключается, рабочий стол работает
- [ ] звук есть

## Шаг 14. Проброс видеокарты (вариант C)

Последний и самый опасный шаг. Делать только когда всё выше работает.

**Сначала — страховка:**

```bash
keel backup                              # свежая копия конфигурации хоста
cp /var/lib/vz/dump/keel-config/keel-host-*.tar.gz куда-нибудь-не-сюда
```

Включаем в манифесте:

```jsonc
"host": {
  "gpu_passthrough": { "enabled": true, "device": "auto", "vm": 201 }
}
```

Смотрим план — здесь видно каждую правку файла до единой:

```bash
keel plan --only host/60-gpu-passthrough
```

Проверь в выводе: IOMMU включён, группа изолирована, загрузчик определён.
Не сошлось хоть в одном — keel откажется, и правильно сделает.

```bash
keel apply --only host/60-gpu-passthrough
```

keel попросит **набрать PCI-адрес видеокарты** — это подтверждение, что ты
прочитал предупреждение про гаснущий монитор. Перед перезагрузкой на экран
выведется инструкция отката: **перепиши её на бумагу или в телефон**, с
погасшего монитора её будет не прочитать.

```bash
reboot
```

Независимая проверка после перезагрузки (по SSH — локальной консоли уже нет):

```bash
lspci -nnk -s 64:00.0     # Kernel driver in use: vfio-pci
qm config 201 | grep hostpci
qm start 201
```

**Обязательно проверь откат** — это половина работы, и она бесполезна, если
не проверена:

```bash
keel gpu status          # что записано
keel gpu revert
reboot
lspci -nnk -s 64:00.0    # снова amdgpu
ls /dev/dri              # узлы вернулись, вариант A снова работает
```

- [ ] план показал все правки до применения
- [ ] подтверждение потребовало набрать адрес
- [ ] инструкция отката записана отдельно от хоста
- [ ] после перезагрузки устройство держит vfio-pci

## Что присылать, если что-то пошло не так

```bash
keel logs > /root/keel-лог.txt          # полный вывод последнего запуска
keel doctor > /root/keel-doctor.txt
```

И по возможности:

- номер шага из этого файла;
- точное сообщение об ошибке;
- вывод команды независимой проверки с этого шага;
- `qm config <id>` или `pct config <id>`, если дело в госте.

Лога и `doctor` обычно достаточно: в логе есть каждая выполненная команда
и её вывод целиком.
