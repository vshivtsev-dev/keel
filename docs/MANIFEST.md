# Манифест: справочник полей

Манифест — файл `manifest/host.json`. Это JSON с комментариями: всё после `#`
или `//` до конца строки игнорируется, висячие запятые допускаются.

**Главное правило: нет ключа — ничего не происходит.** Пустой манифест `{}`
означает «не делай с хостом ничего», и keel так и поступит. Дефолтов,
меняющих состояние, в коде нет.

```bash
cp manifest/host.example.json manifest/host.json
keel validate      # проверить, что нет опечаток
keel plan          # посмотреть, что из этого следует
```

## Разделы

| Раздел | Что описывает |
|--------|---------------|
| `host` | настройки самого хоста |
| `storages` | хранилища |
| `guests` | виртуальные машины и контейнеры |
| `backup` | расписание резервного копирования гостей |

Любой другой раздел — ошибка, и `keel validate` об этом скажет. Это защита от
опечаток вроде `hosts` вместо `host`.

## host

### host.repos

Какой репозиторий Proxmox использовать: `no-subscription` (бесплатный),
`enterprise` (нужна подписка) или `test` (не для рабочих машин).

Выбранный включается, остальные **выключаются, но не удаляются**: в новом
формате (`*.sources`) внутрь записи добавляется `Enabled: false`, в старом
(`*.list`) строки комментируются. Вернуть обратно — одна правка.

Слово «внутрь» здесь существенное. Записи в deb822 разделяются пустой строкой,
и у каждой обязано быть поле `Types`. Дописать выключатель в конец файла через
пустую строку — значит создать вторую запись без `Types`; apt считает такой
файл битым и перестаёт читать **все** источники сразу, а не только этот.

Платный ceph-репозиторий тоже выключается, если выбран не `enterprise`: без
подписки он отвечает 401 и ломает `apt update`.

### host.updates

`true` — ставить обновления через `dist-upgrade` при `keel apply`. Список
пакетов показывается до установки. Перезагрузку keel не делает и не
предлагает — только предупреждает, если она требуется.

Именно `dist-upgrade`, а не `upgrade`: Proxmox иногда меняет состав пакетов,
и обычный `upgrade` такие переходы пропускает, оставляя систему на полпути.

### host.updates_min_speed

```jsonc
"updates_min_speed": "30K"   // по умолчанию; "0" — не проверять
```

Перед закачкой keel измеряет связь до репозитория и, если она медленнее
порога, **не начинает обновление**, а объясняет почему.

Причина не в нетерпеливости. На очень медленной или обрывающейся сети apt
складывает не стартовавшие закачки обратно в очередь и пробует снова; на сотне
пакетов эта очередь растёт быстрее, чем что-либо скачивается. На живом хосте
это однажды довело `apt-get` до 6.4 ГБ и едва не увело машину в OOM. Отказаться
начинать — дешевле, чем потерять хост посреди обновления.

Меряется не выдуманный адрес, а первый из пакетов, которые apt собирается
скачать: он точно существует и лежит там же, куда пойдёт обновление.

Формат — число с суффиксом `K` или `M`, как у `disk`. Заодно keel ограничивает
apt одним повтором и тридцатью секундами ожидания вместо трёх повторов и двух
минут: отказ становится виден сразу, а очередь не разбухает.

### host.config_backup

Копия конфигурации самого хоста. Бэкапы виртуалок делает vzdump, а вот хост —
его сеть, хранилища, список гостей, ключи — не бэкапит никто.

```jsonc
"config_backup": {
  "path": "/var/lib/vz/dump/keel-config",
  "keep": 7,              // сколько архивов хранить
  "max_age_hours": 24     // старше этого — считается устаревшей
}
```

В архив попадают `/etc/pve`, настройки сети, apt, загрузчика, `fstab`,
`authorized_keys`, сам манифест и текстовый снимок состояния хоста
(`host-report.txt`): версии, диски, хранилища, адреса, список гостей.

Держи архив **не на этом же хосте**: копия рядом с оригиналом спасает только
от опечаток.

### host.gpu_passthrough

Полный проброс видеокарты в ВМ — вариант C. Выключен по умолчанию.

```jsonc
"gpu_passthrough": {
  "enabled": true,
  "device": "auto",     // или PCI-адрес, например "64:00.0"
  "vm": 201             // кому отдать; только гость из твоего манифеста
}
```

Самый опасный ключ в манифесте: если видеокарта на хосте одна, после
перезагрузки локальный монитор погаснет навсегда. Что именно меняется, как
проверить и как откатить — [30-desktop.md](30-desktop.md).

Откат: `keel gpu revert`.

### Ставить не всех сразу

По умолчанию `keel apply` делает всех гостей из манифеста. Чтобы поставить
кого-то одного, есть два пути.

**Через меню** — `keel`, затем «Виртуальные машины» или «Контейнеры LXC».
Машины и контейнеры разведены по разным экранам нарочно: в Proxmox это разные
сущности с разными командами и разной ценой ошибки, и в одном списке они
выглядят обманчиво одинаково. В списке видно номер, имя, чем гость будет и есть
ли он уже на хосте; существующие показываются снятыми и с пометкой «не трону».

**Из командной строки** — флаг `--guest` с номерами через запятую:

```bash
keel plan  --guest 201
keel apply --guest 200,201
```

Работает и с `plan`, и с `apply`, и с `verify`. Про пропущенных keel скажет
отдельной строкой, чтобы «уже в порядке» не читалось как «все гости на месте».

Посмотреть список, не открывая манифест: `keel guests`.

## storages

```jsonc
"storages": [
  { "name": "local", "content": ["iso", "vztmpl", "backup", "snippets"] },
  { "name": "media", "type": "dir", "path": "/mnt/media", "content": ["iso"] }
]
```

keel **добавляет** хранилищу перечисленные типы `content` и умеет создать
отсутствующее хранилище **только типа `dir`** — заводить LVM или ZFS
автоматически слишком опасно, это отдельное осознанное решение.

Список в манифесте — это «что должно быть», а не «что должно остаться». Типы,
которые уже есть у хранилища, но в манифесте не названы, сохраняются: на PVE 9
у `local` по умолчанию есть `import`, и терять панель импорта из-за того, что
её забыли переписать в манифест, неправильно. Убрать тип можно руками через
`pvesm set`.

Порядок типов в списке не важен. Хранилища, которых нет в манифесте, не
трогаются вовсе; ничего не удаляется никогда.

`snippets` у `local` нужны для cloud-init: без них ВМ из облачных образов не
настроить, и keel честно откажется её создавать.

## guests

```jsonc
"guests": [
  {
    "id": 100,                 // обязательно, не меньше 100
    "name": "haos",            // обязательно
    "profile": "haos",         // обязательно, см. список ниже
    "cores": 2,
    "memory": 4096,            // МБ
    "disk": "32G",
    "storage": "local-lvm",
    "bridge": "vmbr0",
    "start_on_boot": true,     // автозапуск при загрузке хоста
    "start": true              // запустить сразу после создания
  }
]
```

**Существующий гость с таким id не трогается никогда.** keel сообщит, чем он
отличается от описания, и пройдёт мимо. Приводить работающую виртуалку к
манифесту — решение человека, не скрипта.

Незаданные поля берутся из профиля (`defaults`), а не выдумываются.

### Профили

| Профиль | Что это |
|---------|---------|
| `haos` | Home Assistant OS, ВМ из готового образа |
| `debian-cloud` | Debian 13, облачный образ + cloud-init |
| `ubuntu-cloud` | Ubuntu 24.04, облачный образ + cloud-init |
| `desktop` | рабочий стол; чем закрыть — решает `graphics` |
| `cloudflared` | туннель Cloudflare наружу, отдельный маленький контейнер |

### guests[].graphics

Только для профиля `desktop`. `dri` (по умолчанию) — контейнер LXC с доступом
к видеокарте хоста; `virgl` — виртуальная машина с 3D через virtio-gl.
Сравнение и подробности — [30-desktop.md](30-desktop.md).

### Профиль cloudflared

```jsonc
{ "id": 102, "name": "tunnel", "profile": "cloudflared" }
```

Больше ничего не нужно: размеры берутся из профиля. Токен туннеля keel спросит
при создании и положит в `/root/keel/secrets/cloudflared.txt` — **в манифесте
его нет и не будет**. Что настраивается в панели Cloudflare и что делать,
если туннель не поднялся, — [40-cloudflared.md](40-cloudflared.md).

### guests[].image_version

```jsonc
{ "id": 200, "name": "keel-haos", "profile": "haos", "image_version": "18.2" }
```

Закрепляет версию образа вместо «последней». Для инструмента восстановления это
важнее, чем кажется: закреплённая версия значит, что сборка хоста через полгода
даст тот же результат, что сегодня.

Без этого ключа keel спрашивает последний релиз у GitHub и берёт **имя файла из
ответа**, а не собирает адрес из шаблона: наверху могут переименовать файл или
не выложить его для очередной версии. Если ни найденная версия, ни запасная из
профиля не открываются, keel называет все проверенные адреса и останавливается,
а не качает наугад.

### guests[].cloudinit

```jsonc
"cloudinit": {
  "user": "av",
  "ssh_key_from": "host",           // взять открытые ключи с хоста
  "ssh_key_file": "/root/keys.pub", // либо указать файл явно
  "ipconfig": "ip=dhcp"             // или "ip=192.168.1.50/24,gw=192.168.1.1"
}
```

Для контейнеров используются `user` и ключи; сеть задаётся полем `ip`
(по умолчанию `dhcp`).

### guests[].packages и guests[].runcmd

Списки **добавляются** к тем, что описаны в профиле, а не заменяют их.
`packages` ставятся при первом запуске, `runcmd` выполняются после.

Здесь установка пакетов безопасна — гость создан с нуля этим же запуском, и
ломать в нём нечего. На хосте такого модуля нет намеренно,
см. [BACKLOG.md](BACKLOG.md).

## backup

```jsonc
"backup": {
  "schedule": "02:00",      // календарные события Proxmox: "mon..fri 22:30"
  "storage": "local",
  "mode": "snapshot",       // snapshot | suspend | stop
  "guests": [100, 101],     // либо "all": true
  "keep_last": 3,
  "compress": "zstd"
}
```

Формат расписания — не cron, а календарные события Proxmox: `02:00`,
`mon..fri 22:30`, `*-*-01 03:00`.

Задание помечается комментарием `keel` — по нему keel его и находит при
повторных запусках. Задания, созданные вручную или другими инструментами, не
трогаются.

## Чего в манифесте нет намеренно

**Паролей и токенов.** Только пути к файлам, которые лежат вне репозитория.
Пароли рабочих столов keel генерирует сам и кладёт в `/root/keel/secrets/` с
правами 600; посмотреть — `keel password <id>`. Токен туннеля Cloudflare
живёт там же; посмотреть — `keel token`.

Пароль keel может придумать, токен — нет: его выдаёт панель Cloudflare.
Поэтому без токена keel отказывается создавать туннель, а не поднимает
контейнер, который никуда не подключён.

**Часового пояса, списка пакетов хоста, настроек SSH и сети.** Всё это
выключено осознанно, с объяснением причин в [BACKLOG.md](BACKLOG.md).

Твой манифест лежит в `/root/keel/host.json` — вне каталога с кодом, поэтому
обновление keel до него не дотягивается. В нём адреса, имена и ссылки на
ключи. Если решишь версионировать свой хост — убери строку из
`.gitignore` осознанно.
