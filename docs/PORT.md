# Переход на Go

keel переписывается с bash на Go. Здесь — зачем, что уже перенесено и в
каком порядке идёт остальное.

## Зачем

Три потолка, в которые упёрлась bash-версия.

**`whiptail` — это модальные диалоги и ничего больше.** Показать состояние
хоста, выбор и ход применения одновременно нельзя. На длинном `apply`
человек получает десятки подтверждений подряд и либо жмёт Enter не глядя,
либо ставит `--yes` — в обоих случаях ворота `run()` перестают работать.

**`plan` и `apply` считают изменения дважды.** `modules_plan` и
`modules_apply` независимо вызывают `mod_check`. Между ними состояние хоста
могло поменяться: посмотрел одно — применилось другое. Оговорка в справке
«`--yes` только после того, как посмотрел plan» — это совет, а не механизм.

**Модуль общается текстом.** `mod_check` печатает строки для человека;
структуры данных нет. Интерфейс богаче списка строк построить не на чем.

## Что это меняет в принципах

Одно решение из `PLAN.md` переворачивается, остальные — усиливаются.

Обоснование bash звучало так: «инструмент восстановления, который перед
работой требует `apt install`, — плохой инструмент восстановления». Оно
верное, и именно поэтому bash уходит. Статический бинарник (2,4 МБ,
`CGO_ENABLED=0`) не требует **ничего**: ни `perl` с `JSON::PP`, ни
`whiptail`, ни даже совместимой libc. Зависимостей становится меньше, а не
больше.

Остальное остаётся как было: правило нуля, «ничего вне манифеста не
трогается», каждое изменение через одни ворота, запуск на самом хосте,
никакого веб-дашборда.

## Что нового в устройстве

**Провайдер вместо модуля.** Провайдер ничего не выполняет — он возвращает
список шагов. Раньше модуль сначала печатал в `mod_check`, что собирается
сделать, а потом делал это в `mod_apply`: те же ветвления, написанные
дважды, и ни одной гарантии, что второй раз получится то же самое.

**План — это файл.** `keel plan` сохраняет набор шагов в
`/root/keel/plans/`, `keel apply` исполняет **именно его**. Перед
применением сверяются отпечатки манифеста и состояния хоста: разошлись —
план объявляется устаревшим. Подтверждать становится нечего вслепую.

**Вопросы задаются до плана.** Пароль рабочего стола и токен Cloudflare
спрашиваются на этапе сборки плана, а не посреди применения. В план идёт
ссылка на файл в `secrets/`, самого секрета там нет и быть не может.

**Экран вместо диалогов.** Bubble Tea: дерево ресурсов с подсвеченным
дрейфом, сводка выбранного и ход применения — одновременно. Две раскладки:
широкая и аварийная, для консоли Proxmox и телефона по SSH.

## Порядок

| Этап | Содержание | Состояние |
|---|---|---|
| 0 | Каркас: манифест, факты, пути, ворота, план, страж, `doctor`, `validate`, сборка | готово |
| 1 | Движок плана и провайдер хранилищ | готово |
| 2 | Репозитории, обновления, задания бэкапа, копия конфигурации | |
| 3 | Гости и профили | |
| 4 | Проброс видеокарты с откатом | |
| 5 | Интерфейс: широкая раскладка | |
| 6 | Аварийная раскладка, кириллица, долгие команды | |
| 7 | Установка: sha256, `keel update`, раздача через Dokploy | |
| 8 | Документация, удаление bash | |

До этапа 8 обе версии лежат рядом и обе работают. Рабочей остаётся
bash-версия — `bin/keel`; новая доступна как `go run ./cmd/keel`.

## Как проверять

```bash
go test ./...        # разбор манифеста, факты, план, страж ворот
go vet ./...
docker compose up --build     # сборка и раздача, как в Dokploy
curl -fsS localhost:8080/checksums.txt
```

Самая честная проверка порта — `./tests/parity.sh`: один и тот же манифест
и один и тот же подставной хост подаются обеим версиям, и списки команд
сверяются дословно. Тесты каждой версии проверяют её собственные ожидания,
а здесь две независимые реализации сверяются друг с другом.

```bash
./tests/parity.sh            все перенесённые области
./tests/parity.sh storage    только одну
```

Список команд, которые уйдут хосту, можно посмотреть и руками:

```bash
keel plan --commands
```

## Страж ворот

`internal/provider/guard_test.go` разбирает исходники провайдеров и падает,
если туда пробрался `os/exec` или запись в файл. Это наследник
`tests/lint-run-guard.sh`, но строже: проверка идёт по дереву кода, поэтому
её не обойти ни переносом строки, ни переменной с именем команды.

Если он упал — не добавляй исключение. Опиши изменение шагом плана, и его
выполнит движок, показав команду до того, как она случится.
