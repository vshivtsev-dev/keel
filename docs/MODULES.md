# Как устроен модуль

Модуль — это один файл в `modules/`, который отвечает за одну область хоста.
Больше от него ничего не требуется: четыре функции и никакой магии.

```bash
mod_title()     # одна строка для меню
mod_describe()  # что модуль делает, человеческим языком
mod_check()     # нужно ли что-то менять
mod_apply()     # привести к нужному состоянию
mod_verify()    # проверить постфактум
```

## Коды возврата

Договорённость на весь проект: **0 всегда значит «всё хорошо, делать нечего»**.

| Код | Константа | Смысл |
|-----|-----------|-------|
| 0   | `KEEL_RC_OK` | состояние уже такое, как описано в манифесте |
| 10  | `KEEL_RC_CHANGES` | есть что изменить |
| 20  | `KEEL_RC_SKIP` | в манифесте нет соответствующего ключа |
| иное | — | ошибка: непонятное значение, недоступный файл и так далее |

`KEEL_RC_SKIP` — это правило нуля в действии. Нет ключа в манифесте — модуль
молча ничего не делает. Не «разумный дефолт», не «обычно так лучше».

## Главное правило

**Всё, что меняет систему, идёт через `run()` или `run_write()`.**

```bash
run "Обновить список пакетов" apt-get update

printf '%s\n' "$content" | run_write "Включить репозиторий" /etc/apt/sources.list.d/pve.sources
```

Эти две функции показывают изменение до того, как оно случится, спрашивают
подтверждение, делают резервную копию файла и пишут всё в лог. Прямой вызов
`apt-get`, `qm`, `sed -i` или запись в `/etc` мимо них — ошибка: её ловит
`tests/lint-run-guard.sh`, который входит в `./tests/run.sh`.

## Чтение манифеста

```bash
config_get host.repos              # значение или пусто
config_get guests.0.name "имя"     # со значением по умолчанию
config_len guests                  # длина массива
config_bool guests.0.start_on_boot # true/false
config_has host.repos              # есть ли ключ вообще
```

## Факты о хосте

В `lib/pve.sh` лежат функции только для чтения: `pve_major`, `deb_codename`,
`pve_repo_style`, `pve_bootloader`, `gpu_list`, `iommu_group_of`, `dri_nodes`
и другие. Их можно свободно звать из `check` и `verify` — они ничего не меняют.

## Пути к системным файлам

Системные пути стройте через `fsroot`:

```bash
fsroot /etc/apt/sources.list.d/pve.sources
```

В обычной работе это пустая обёртка. В тестах `KEEL_FS_ROOT` указывает на
временный каталог, и модуль проверяется по-настоящему, но мимо живой системы.

## Порядок запуска

Порядок задаёт **числовой префикс имени файла**, а не каталог: гости должны
создаваться после хранилищ, в каком бы каталоге эти модули ни лежали.

```
host/10-repos  →  host/20-updates  →  host/30-storage
    →  host/40-backup-jobs  →  guests/50-guests  →  host/90-config-backup
```

Шаг между номерами — 10, чтобы можно было вставить модуль между
существующими. Файлы, чьё имя начинается с `_`, модулями не считаются —
это библиотеки для них.

## Временные файлы

`run-guard` запрещает в модулях любые `rm`, `cp`, `mkdir` — он не разбирает,
куда именно они направлены. Если модулю нужно поработать с временными
файлами, эта работа выносится в `lib/`: там ей и место, а модуль остаётся
описанием того, что происходит с системой.

Готовые помощники: `keel_tmp_cleanup <каталог>` в ядре, `mktemp` внутри
библиотечных функций.

## Шаблон

```bash
#!/usr/bin/env bash
# shellcheck shell=bash

mod_title() { printf 'Название для меню'; }

mod_describe() {
  cat <<'EOF'
Два-три предложения о том, что модуль делает и чего не делает.
EOF
}

mod_check() {
  local value; value=$(config_get host.что_то "")
  [[ -n "$value" ]] || return "$KEEL_RC_SKIP"

  if состояние_уже_нужное; then
    return "$KEEL_RC_OK"
  fi
  printf 'что именно изменится\n'
  return "$KEEL_RC_CHANGES"
}

mod_apply() {
  local value; value=$(config_get host.что_то "")
  [[ -n "$value" ]] || return "$KEEL_RC_SKIP"
  run "Понятное описание шага" команда аргументы
}

mod_verify() {
  состояние_уже_нужное && return "$KEEL_RC_OK"
  printf 'что не сошлось\n'
  return "$KEEL_RC_CHANGES"
}
```

## Гости — особый случай

Виртуальные машины и контейнеры описываются не модулем, а парой
«манифест + профиль»:

- в манифесте — что должно быть: id, имя, ресурсы, профиль;
- в `profiles/<имя>.json` — как это собрать: откуда образ, какого рода гость
  (`vm-image`, `vm-cloudinit`, `lxc`), какие умолчания и пакеты.

Модуль `guests/50-guests` только обходит список и передаёт работу
`lib/guests.sh`. Чтобы добавить новый вид гостя, обычно достаточно нового
профиля — код трогать не нужно.
